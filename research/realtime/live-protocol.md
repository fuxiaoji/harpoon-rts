# M1c/M1d 持续时钟与唤醒诊断：接口契约

本文件随工作区实现更新；M1c原始语义以该批冻结副本为准。2026-10-22的M1d新增两次变化、通知计数、任务版本重新触发和过期过滤，不能将其收益回填给M1c。

本原型使用本项目生产导航核心。私有裁判单独进程持有未来任务事件；Python控制器只接收本方observation、当时公开任务和当前站令revision。真实模型在工作线程的独立Codex进程中响应；主循环按单调墙钟目标逐秒推进引擎，不等待模型。它与M1b“先拿回复再延迟回放”分开命名。

## 场景与时钟

D0/D1沿用M1a模板。D2在新协议中将更新后窗口改为300模拟秒；单位、目标生成、事件相位和动作不变。该窗口依据旧简单任务约9–11墙钟秒的响应、10倍模拟映射与约140模拟秒的及时航行量级预先选定；只是新的校准起点，不保证各策略可行。旧180秒数据保留，不合并。M1c/D2初始世界与D1配对，仅期限不同。

完整模拟时长1200秒；首批真实步速100ms/tick，目标总墙钟120秒。每tick记录实际观察墙钟与目标时刻的偏差，迟到时追赶，不能把操作系统调度抖动当作精确节拍。单个在途请求，等待期间原航路持续，触发合并并保存最早时刻。响应先校验，于下一tick生效；任务更新先于旧结果执行，revision/截止在接收与生效两处检查。hold不把尚未执行的新任务标成已跟随。

运行顺序：按协议等待该tick → 发布私有事件及校验待执行响应 → 生产核心步进 → 获取本方观察 → 接收已完成响应并校验 → 监视触发 → 如空闲且额度允许发出请求。只有一方承担任务，另一方远处控制单位不参与交战。这里的成功是到点任务成功，不是海战胜率。

## 唤醒方式

| 代号 | 定义 |
| --- | --- |
| F60/F300/F600 | T0起算固定60/300/600模拟秒网格；事件不重置网格，T0不调用 |
| EH | 人工条件：`task_mismatch == 1`的假到真边沿 |
| EM | T0调用模型生成条件并计入预算，之后只按其条件唤醒；无隐式定时兜底 |
| HH600 | EH或T0起算600秒网格 |
| HM600 | EM或T0起算600秒网格；初始化同样计费计额度 |

模型每次均返回相同动作schema、简短说明及wake_conditions，固定组和人工组不使用所生成条件。如此控制提示与输出接口的差异；它不等同于针对每种策略最小化输出开销后的成本比较。每局统一最多6次调用，初始化、无益、失败、过期和重复调用均计数；这只是调用次数上限，不是token/金额严格匹配。首批统一low推理档，推理档不是人为延迟。

人工和模型条件采用同一受限数值DSL：至多3个OR条件，每个至多3个AND比较；字段为tick、task_revision、standing_revision、task_mismatch、distance_nm、deadline_remaining_s、plan_age_s；比较为eq/ne/lt/le/gt/ge。数值有限，禁止任意代码或裁判字段。每个条件只在假到真时触发；安装即为真的条件也触发一次，条件变假后重新武装。模型条件只在合法响应生效后替换。错误或空条件可能漏唤醒，不补免费模型调用；带定时兜底者单独报告。

## 数据、校验和研究边界

保存协议与顺序、冻结源码/二进制哈希、逐tick位置和墙钟偏差、请求观察、最早触发/发出/工作线程开始/响应/校验/生效时间、最终计划和结构化规则、提供方用量与失败。金额缺失，不保存reasoning文字。`monitor_wall_ns`为墙钟测量；首批旧字段名`monitor_cpu_ns`实际也来自perf_counter，分析按墙钟解释，不是CPU占用。

Rust按已执行命令独立重演完整World；Python从公开任务和位置独立重计分，并重建人工/模型条件全部边沿，核对实际触发和每次模型特征。旧请求在生效前遭遇新revision的边界另有测试。脚本快速验收采用1ms目标tick，Windows实际调度误差可能达十余tick，只验逻辑/重演，不冒称真实1kHz节拍。

首批真实矩阵为一个种子的D2七臂，另加D0/D1的EH两对照，总9局，每局保留全部1200模拟秒。顺序在调用前随机冻结，逐局顺序运行，避免人为共享请求槽造成臂间排队。单种子、无重复采样不提供一般排名或显著性结论；倍速后补实验单独保存，不与主批合并。M2正式实验仍需更多事件相位/种子、D5干扰、成本匹配和留出任务。M3复杂度有效性、M4联合方法、M5确认及L2交战继续待办。

当前只验收单次变化。若一个条件持续为真，在途期间再发生新revision不会自动产生第二个布尔边沿；原回复随后若过期，纯事件组可能没有新的唤醒。D5前须加入双方共用的事件身份/变化脉冲或明确重试协议，并用两次密集更新检验锁存，不能默认现有单变化通过就解决了该问题。另须为各组加入公平的已过期任务廉价过滤；当前原始调用账保留所有过期调用，分析另标其可避免部分，不能拿这些开销证明对强固定基线的优势。

## M1d v2：密集更新与公共执行语义

上段描述M1c历史限制。v2保留旧语义作为失败对照，并增加两个独立开关。`--revision-keyed`让每条条件在假到真时触发，也在条件持续为真且公开任务revision变化时触发；安装时为真仍触发一次。同一revision的常规重复通知不会重新触发这个任务条件；模型若显式写通知阈值，仍按其条件执行。人工与模型共用此语义，不赋予任何一组免费模型重试。若第二次变化发生于在途期间，触发仍进入同一个合并锁存，旧回复照常拒收、照常计费。

`--skip-expired`在当前公开截止之后清除锁存触发，各方法都不能再为该过期任务发起调用；已经在途的调用保留并计成本。过滤记录的是被丢弃的触发，不自动等同于节省的调用数，因为终局等情况本来也不允许发起请求。新任务出现后须由新的有效事件/时间网格触发，已清掉的旧触发不会复活。

D5是最小双变化压力例：从D1同初态/首变化生成器出发，在首次公开变化后30模拟秒发布第二个目标，目标相对第一目标东移0.15海里并关于东西轴镜像；第二次有效期900秒。每30秒投递一次常规重复通知，共39次，不改变任务revision。第一次与第二次变化的时间、目标均由裁判持有，未公开前不传给控制器；模型不能看到D5标签、种子或未来事件列表。每次输入只增加当前公开通知计数`public_notice_seq`与其含义，DSL加入第8个字段`notice_seq`。这不是传感器噪声或完整D5任务族。

40局脚本验收使用0–3四个开发种子、旧/新两种配置，每配置含D5的EH/EM、D2的F300/F600及D0的EH。脚本请求真实等待80ms，1ms目标tick只作故障复现；实测时长和Windows节拍误差保留。D5没有触发过期过滤，检验任务版本重新触发；D2固定组不使用事件监视器，检验过期过滤；D0检查无变化时零额外调用。这是按机制隔离的功能检查，非完整两因素统计试验。

后续真实验证单独冻结为seed7、200ms/tick、low、最多6次调用、D5 EH/EM各一局，使用两个开关。它检验真实调用下在途变化、旧回复拒收与新请求接续，不提供一般胜率比较。启动调用失败/过期而尚未安装任何条件时的恢复，以及在途进程的跨进程恢复仍待实现。

## 运行

从`harpoon-rts`执行，必须使用新证据目录；默认复制M1b已冻结的生产核心，覆盖新桥/控制器，不把其他聊天的生产改动混入本研究：

```powershell
python scripts/run-realtime-live.py --out E:/CodexBuilds/live-script-new --backend scripted --tick-ms 1 --seeds 7,8
python scripts/run-realtime-live.py --out E:/CodexBuilds/live-model-new --backend codex --tick-ms 100 --seeds 7
python scripts/analyze-realtime-live.py --batch E:/CodexBuilds/live-model-new
python scripts/run-realtime-live.py --out E:/CodexBuilds/dense-new --episode d5:eh --episode d5:em --tick-ms 200 --revision-keyed --skip-expired
```

可用`--base-source`指定具有同一模板/核心依赖的源码副本。`--episode d2:eh --episode d2:f60`选择新批次子集，`--tick-ms 200`作5倍速敏感性检查。基线模板、规则JSON及原Cargolock一起冻结；当前未实现携带在途模型进程的跨进程恢复。
